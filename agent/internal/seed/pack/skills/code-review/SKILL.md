# Skill: Code Review（代码库全面审查）

## When to use
- 用户要求"全面审查/代码审查/体检"自己的项目代码库
- 排查性能瓶颈、代码缺陷、可维护性差、安全漏洞、重复代码
- 重点排查某类异常（如前端页面跳转异常、接口报错）需要定位根因时
- 交付前/上线前的质量收口检查

**边界**：单点 bug 修复走 `debugging-fixing`；PR/MR 协作评审走 `review`（gstack）；焚诀自身技能路由审计走 `fenjue-memory-audit` / `A-skill-manager`。

## 审查五维（每维都要过，证据落到 file:line）
1. **性能瓶颈**：N+1 查询、每请求全量重算无缓存、同步阻塞外部调用、无界内存增长（缓存/桶/会话）、O(n²) 热路径
2. **代码缺陷**：边界条件（空值/空集/越界）、异常路径静默吞错、并发竞态（TOCTOU）、会话/Cookie 容量上限、资源泄漏
3. **可维护性**：同一逻辑多处实现且已漂移（重复实现收敛为唯一真相源）、弃用 API、god-module（拆分需权衡回归风险，测试钉死的模块记录不拆）、魔法值散落
4. **安全漏洞**：注入面（SQL/XSS/命令）、越权（角色装饰器覆盖全路由）、认证频控（登录/写接口限流）、密钥硬编码（一律环境变量）、CSRF/Cookie 属性（HttpOnly/SameSite/Secure）
5. **重复代码**：跨文件复制的工具函数/关键词表/校验逻辑 → 收敛到单一模块导出

## 工作流
1. **现状核验（G7）**：动手前以磁盘实测（git status/diff/mtime/SHA256）重建现状，禁用旧记忆当事实
2. **全量扫描**：按五维逐文件审读；目录级先用 grep/wc 摸底（行数分布、链接拓扑、依赖图）
3. **专项排查**：用户点名的异常单独深挖（静态分析 + 实测复现），区分「真缺陷 / 设计使然 / 降级体感」
4. **优先级评定**：严重程度（高/中/低）× 影响范围（全局/模块级/局部）综合定级，从高到低逐项实施
5. **修复前陈述数据流假设**：来源/流向/结构/异常路径四要素，未陈述不得编码
6. **增量实施**：每项修复 → 立即验证（lint/build/测试/冒烟）→ 简要汇报；同文件编辑串行并在改后 grep 验证落盘
7. **验证收口**：全量门禁/测试套件复跑；改动同步权威副本并 SHA256 复验；git commit 留回滚锚点

## 报告模板（每条记录六字段）
| 字段 | 要求 |
|---|---|
| 问题编号 | P0/P1/P2/P3-序号 |
| 优先级等级 | 高/中/低 × 全局/模块级/局部 |
| 所属模块 | 精确到文件路径 |
| 问题描述 | 具体可追溯（含 file:line 证据） |
| 优化目标 | 修什么、为什么 |
| 预期效果 | 修后可验证的行为变化 |

**记录不修**清单：回归风险 > 收益的项（如测试钉死的 god-module 拆分）须附不修理由。

## 经验锚点
- 修复引入回归（如限流让既有测试套件连续登录触发 429）→ 测试套件补环境开关 + 新防线在冒烟专项段补断言
- 清理"垃圾"产物前必须先做独有内容比对（SHA256）+ mtime 复核，复核结果要在删除动作**之前**读完
- 文档/注释中的路径类断言随目录迁移必然过期，审查时以磁盘实测为准

- 性能审查先做导入税归因：子进程型 CLI 用逐模块 __import__ 计时定位急性导入（实证 2026-09-23：bge_layer.py:15 模块级 sklearn 0.91s 占冷调用 70%，direct 短路路径并不使用它），再决定懒导入/常驻化，勿直觉归因模型推理


## 反理性化（借口 → 反驳，出现左列念头即停手）

| 借口 | 反驳 |
|---|---|
| 「挑了几处明显的坏味道，就能报『全库已审』」 | 审查范围要能对账：实际读过的文件数 / 目录内文件总数 必须写明，未覆盖的目录点名列出 |
| 「问题描述清楚了，行号待会儿补」 | 没有 `file:line` 的结论无法复核也无法修，等于没提；每条记录定稿前先补定位 |
| 「静态读代码就够了，跑构建和测试太花时间」 | 不跑就分不清"看着有问题"和"真会失败"；至少过一遍编译/测试，把失败输出贴进报告 |
| 「这是别人写的老代码，不改它就没风险」 | 老代码里的漏洞仍在生产路径上；按严重程度评级照提，是否修由人定，不由我预判 |
