## 2. 三档规模与沙箱隔离

| 档 | 平台数 | 技能数 | 库文件数 |
|---|---|---|---|
| S1 | 9（与生产同量级） | 50 | 500 |
| S2 | 50 | 300 | 3 000 |
| S3 | 200 | 1000 | 10 000 |

沙箱是硬要求，不是可选：公开仓与私有记忆源在同一台机器上，`enable` 会写备份到
`~/.fenjue/trash`，`serve` 每次启动都会改写 `~/.fenjue/token`。脚本因此

1. 自造假 `platforms.json`（假平台 id、假库根），一切写入落在仓内 `_temp/bench/`；
2. 给子进程注入 `USERPROFILE` 与 `HOME` —— Go 侧 `safeio.HomeDir` 走 `os.UserHomeDir`，
   即读这两个环境变量，于是 hub 以为的 `~/.fenjue` 落在沙箱里；
3. 端口向系统动态申请（`pick_free_port`），固定端口在「上次被中断」或「并行跑两份」时会假失败。

**隔离实测证据**：压测前后真实 `~/.fenjue/token` 与 `logs/agent.log` 的 mtime 分别为
18:37:25 / 18:37:30，压测运行窗口为 22:05:56–22:06:30，两者均**未变化**，真实 `trash`
备份目录数（19）也未增加。

## 4. 结论（每条都对应代码里的一处，不靠猜）

### 4.1 冷启动与库规模无关

S1 → S3 库文件从 500 涨到 10 000（20 倍），冷启动始终在 **0.50–0.55 s**。原因在
`seed.Bootstrap`：只在空库播种，且播种前对固定的 29 个内嵌文件做 SHA-256 全量校验
（`seed.VerifyPack`）。**记忆库长到多大都不影响启动时间**。

### 4.2 单端启用成本恒定

平台数 9 → 200（22 倍），单端启用中位数在 **69–215 ms** 之间波动，没有随端数上升的趋势。
每端成本互相独立，没有全局串行化。

### 4.3 挂载吞吐与技能数无关，但绝对值偏低

技能数 50 → 1 000（20 倍），吞吐稳定在 **40–65 links/s**。这是线性扩展的证明，同时
**也是一个真实短板**：以 45 links/s 估算，单端 1 000 条技能链接需要约 22 秒。
瓶颈是 per-skill 的并发上限（`mount/perskill.go`）而非磁盘 IO —— 每次链接创建在 Windows 上
是一次 junction 系统调用。若要缩短，方向是提高并发上限或做批量 API，不是换挂载形态。

### 4.4 全量校验随（平台数 + 技能数）线性增长，与库文件数无关

| 档 | 需探活条目（平台数 + 3 × 技能数） | `verify_ms` |
|---|---|---|
| S1 | 159 | 149.2 |
| S2 | 950 | 238.0 |
| S3 | 3 200 | 951.8 |

代码依据在 `state/verify.go`：`statusPerSkill` 会 `ReadDir` 技能根并**逐条**探活每个技能链接，
而 memory 根只被 `stat` 一次。所以 verify 的成本挂在「挂载点数 + 技能条数」上，
**不随记忆库文件数增长**（10 000 个库文件对 verify 的贡献约等于 0）。10 000 文件那次测到
951.8 ms 仍属可接受，但若技能数继续上升，verify 会成为最先变慢的一环。

### 4.5 常驻内存

11.2 MB（S1）→ 13.8 MB（S3），随规模缓增。⚠️ 见 §1 的边界：这是**内嵌前端缺失**口径的下界。

## 5. 抖动与不可推广之处

| 事项 | 处置 |
|---|---|
| 同档重跑抖动可达 3 倍 | 一次全量连跑曾测到 S1 单端启用 4 597.6 ms（干净值 215.4 ms 的 21 倍），`go build` 也从 2.0 s 变成 63.0 s。**该样本已丢弃**，不进本表。原因是磁盘 I/O 饱和与实时扫描。所有指标取中位数并附复算命令，请在自己的机器上重取 |
| 内嵌前端缺失 | §1 已声明，RSS 为下界 |
| 未测的指标 | 并发请求压测（HTTP 并发 QPS）、跨平台差异（本次仅 Windows）、长跑内存漂移（进程跑一天后的 RSS）。**这三项本文件没有数据，不作任何断言** |
| 二进制签名 | 与性能无关，见 ROADMAP G11（付费证书，BLOCKED） |

## 6. CI 接入方式

`ci.yml` 的 `bench` job 以 **`continue-on-error: true` 的 advisory 腿**接入，与既有 `parity`
腿同一约定。理由：共享 runner 的性能数字抖动大（见 §5），接进阻断链只会制造与代码无关的红。
本文件的数据以本地实跑为准，CI 的作用是「脚本没坏」，不是「性能达标」。

## 7. 复算

```bash
python scripts/bench_scale.py --selftest    # 度量函数自测: 空样本必须 UNVERIFIED, 不得折算 0
python scripts/bench_scale.py               # 三档全跑, 文本表格
python scripts\bench_scale.py --json       # 机器可读, 同时写 _temp/bench/latest.json
python scripts\bench_scale.py --scale S1    # 只跑一档
python scripts\bench_scale.py --keep        # 保留沙箱供人工检查 (默认跑完即删)
```

沙箱里的假平台 id 为 `bench000...` 与 `benchperskill0..2`，库根与平台 home 全在
`_temp/bench/<run-id>/` 内。跑完若要手工清理：`cmd /c rmdir /s /q _temp\bench`
（用系统原生命令，不要用 `shutil.rmtree` —— 它在 Windows 上会跟进 junction，撞上重复删除）。
